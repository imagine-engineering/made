Use the native specification workflow when a feature involves consequential product or architecture decisions, unclear acceptance behavior, or a request for specification review or drift. Answer quick questions and make bounded, well-defined edits normally. A substantial feature can begin from ordinary language. Use inspect to enter design mode and load the project's existing principles, then clarify decisions with the user in chat. Skip questions already answered. There is one editable spec. Describe observable behavior, alternatives and decisions, prioritized scenarios, edge cases, and stable acceptance criteria (AC-001, AC-002, and so on). Avoid copying the conversation, private context, or unnecessary excerpts into the spec.

Use EARS-style wording where a trigger adds precision. Write “When [event], the [system] shall [observable response]”, “If [condition], the [system] shall [observable response]”, or “While [state], the [system] shall [observable response]”. A plain observable criterion is enough without a trigger. For meaningful invariants, write a separate item in the same spec, such as “- PROP-001 (AC-001) For any [inputs and preconditions], [observable rule holds].” Specify the input domain and exceptions so a test can distinguish a pass from a failure. Add properties where the feature has an invariant that a single example cannot express.

Draft only after clarifying decisions that affect the specification. Review the saved draft with the native workflow. Include only explicitly relevant project-relative references and explain what the reviewer can see. Ask Goldfish to check each property's acceptance link, input domain, preconditions, and observable result. Assess the independent findings with the user. Revise in place and re-review a changed revision. Discuss unresolved trade-offs in chat. Propose explicit approval on the reviewed revision after the user resolves major findings. Do not assume consent from the original feature request.

After approval, prepare plan.md and tasks.md using the approved document. Preserve existing files and task progress. Use Spec Kit checkboxes, for example "- [ ] T001 Add record validation (AC-001)". List prerequisites as “Depends on: T001”. Assign each property to a task that also cites its acceptance criterion, such as “- [ ] T002 Check duplicate precedence (AC-001, PROP-001)”. Start each implementation task with begin_task, execute its scoped work, run actual checks using the terminal, and record the observed result with record_check. Pass the terminal receipt ID, the acceptance criteria checked, and the property IDs actually asserted by that check. Use generated, varied or exhaustive inputs where useful for an invariant. A check that exercises one example earns only the coverage it demonstrates. Show failed or unverified criteria and properties explicitly. Complete each task with complete_task. For a completed task with missing or stale evidence, begin the task again to run and record its checks. Preserve its existing completion checkbox. Ask for a user decision if implementation uncovers a material design change, then return to revision and review. Keep workflow metadata managed by the native tools. Resume and check exact status with status. If the user asks for a drift check, inspect the referenced code and use drift with those selected files. Keep any remediation for a separate user decision.
