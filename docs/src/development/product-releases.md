# Preparing product releases

The release sequence is **create tag → manually prepare draft → review packages →
click Publish release**. Branch pushes, tag pushes, and completed CI do not prepare
or publish a release. No permanent `release` branch is required. The legacy
`release.yml` and `release_promotion.yml` identities are inert manual placeholders;
`script/trigger-release` and `script/create-draft-release` fail with migration
instructions. Archived workflows and websites are historical and are not changed.

## Catalog and eligibility

`products/flavors.toml` owns each product's release tag prefix, identity,
qualification status, supported targets, packaging templates, updater namespace,
required CI workflows and administrator enablement variable. Copper uses `copper-v<semver>`. The 2026-11-05 prefix migration was explicitly
requested before any release tag or GitHub Release existed; product ID `rust`,
artifact names and updater namespace remain unchanged. Planned Groovy reserves `jvm-v<semver>`; Forge reserves
`game-v<semver>`. These entries remain planned and cannot be prepared or bundled.
Unknown, overlapping, ambiguous and malformed prefixes/versions are rejected.

`release_prepare.yml` is generated by `tooling/xtask/src/tasks/workflows/release.rs`.
Run it **from main**, with `release_tag` and optional `preparation_scope` (default `full`). `cargo xtask release-version --tag`
peels an existing lightweight or annotated tag to its exact commit and requires
`origin/main` ancestry. The preparation script independently checks GitHub's tag,
repository identity, current main ancestry and the latest exact-SHA, same-repository
main-push run for **every catalog-required CI workflow**. Each must be completed
and successful. PR/fork runs, skipped, cancelled, missing and failed CI do not
qualify. A newer failing attempt invalidates an earlier success. The selected tag
must include the current release machinery and have passed its CI. The tagged
catalog supplies the package identities, templates and target matrix, so later
main catalog changes do not change that tag’s packages. Current qualification
gates remain required; retired target cells are rejected. Required CI is the union
of the current and tagged product requirements. Read-only plans use
`bundle --catalog-commit <SHA> --dry-run`; actual bundling always uses its checkout.

The existing `COPPER_RELEASE_ENABLED=true` repository variable remains the explicit
Copper qualification gate. Its former `COPPER_RELEASE_BOOTSTRAP_SHA` variable is
unused. Do not enable Groovy or another product until its existing release
requirements have been qualified. This implementation does not certify those
requirements, native-agent models or production signatures.

## Version, channel and package isolation

The tag supplies the full semantic version; there is no release version/bump input
and no initial-version fallback in preparation. Stable tags select `stable` and
prerelease tags select `preview`, with the corresponding distinct application IDs,
data namespaces and Windows installer IDs. Build metadata is retained. Numeric
version components must fit platform package fields (0–65535).

`RELEASE_VERSION` reaches every application and remote-server build and the
product-aware bundler. File names contain the product ID and full version.
Windows PE strings and installer display versions retain the semantic version;
Windows numeric resources and Inno `VersionInfoVersion` use its numeric X.Y.Z core.
macOS numeric CFBundle version fields use X.Y.Z and `ProductReleaseVersion` retains
the exact semantic version alongside the compiled application version. These are
platform encodings of the same selected version, not independent release numbers.
Apple requires numeric [short version](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleshortversionstring)
and [build version](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion) fields.
Upstream crates and dependency versions are unchanged.

Only the selected product's catalog targets enter the runtime matrix. Copper's
required targets are Linux x86_64, macOS ARM64 and Windows x86_64. Application and
remote-server builds stay separate to preserve feature boundaries, then converge
on the existing packaging owner:

```sh
RELEASE_VERSION=<tag-version> cargo xtask bundle --product rust \
  --platform <platform> --target <triple> --channel <stable-or-preview> \
  --phase package --signing required
```

There is no signing implementation in workflow YAML. Existing platform scripts
sign nested executables/libraries and the managed llama.cpp runtime; macOS requires
Developer ID signing, notarization and stapling; Windows requires trusted signing
and RFC3161 timestamps; Linux requires a detached GPG archive signature plus its
public key. Platform smoke checks verify the final distributable and installed
contents before producing a SHA-256-bound verification receipt. Missing credentials,
trust failures or missing artifacts fail the workflow; development builds still
support `--signing off` and credential-free `auto`.

## Drafts, checksums and recovery

`draft_product` is the only contents-write job, and requires all package rows.
It downloads only artifact names in the selected product's approved matrix from
**this run**. Bundle plans, licenses and intermediate binaries are bound to commit;
intermediate binaries also bind product, version, channel and feature set. Final
receipts bind the exact package hash to product, tag, version, channel and SHA.
The final upload step checks the Linux archive signature again.

The draft contains platform packages, Linux signature/public key, platform
verification receipts, a product/version verification manifest, SHA256SUMS, notes,
and links to the preparation run and required CI evidence. Notes identify the
product/version/channel and link to comparison with an earlier published release
of the **same product and channel**. They do not copy unscoped commit messages
from the shared repository into a product changelog. If no baseline exists, notes
identify that product, version and commit. Maintainers review the comparison and
curate product-visible highlights before publication.

Preparation never creates or moves a tag. It resolves the remote tag again before
draft creation and **every asset upload**, checks the release is still an owned
draft, and rejects a published release. A matching existing asset is reused only
when GitHub reports the identical SHA-256 digest. Unexpected, partial-upload or
changed assets fail clearly; no `--clobber`, automatic deletions or unsigned fallback
is used. Rerunning failed jobs against identical artifacts can resume partial
uploads. Reruns preserve an existing reviewed/edited draft body. A full rebuild
may produce different timestamped signatures: in that case
review the incomplete draft and its artifacts manually, or select a new version/tag;
preparation will not silently replace them. Do not publish a draft marked
“preparing” or “Preparation is incomplete”. Wait for a successful preparation run.
GitHub does not provide an atomic conditional publish/upload lock against a human
publishing concurrently; every mutation is preceded by the draft/tag guard.

## Publication and updater boundaries

Only a human clicking **Publish release** publishes. Draft creation sets
`make_latest=false`; the repository-global GitHub “Latest” designation is never an
updater input. `script/product_release.py latest --product rust --channel stable`
(and `script/get-released-version rust stable`) enumerates published releases,
filters the catalog prefix and matching prerelease channel, excludes drafts, and
selects the highest semantic version. A newer Groovy release cannot become Copper's
latest release or vice versa. Preview does not consume stable releases.

The existing application updater retains `rust/<channel>` request paths and checks
the returned product ID. Exact-version and release-note requests retain prerelease
identifiers. A reviewed service at compile-time `ZED_PRODUCT_UPDATE_BASE_URL` is
still required; this task does not deploy an update server or turn the GitHub
repository-global latest endpoint into a feed. Its implementation must apply the
same catalog/product/channel/draft filters before enabling updates.

`website_refresh.yml` subscribes only to `release: published` plus explicit manual
recovery for an **already published** Copper tag. It verifies publication before
sending a website webhook, and never runs as part of preparation. GitHub documents
that `published` covers both stable and prereleases, including publication of a
draft: [release events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release).
No archived website is modified. Publication and website refresh remain separate
outcomes: a refresh failure never removes or republishes packages.

## Administrator setup

Use repository secrets or organization secrets explicitly allowed for this
repository. These jobs read them directly; environment-only secrets require a
separately reviewed job/environment binding and will not satisfy preflight.
No private values belong in source, chat or logs. The built-in `GITHUB_TOKEN` needs actions-read for eligibility and
contents-write **only in draft_product**; no personal token is needed to create
the draft. Human publication generates the post-publication release event.

| Platform                  | Required GitHub secrets                                                                                                                                                                          |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| macOS                     | `MACOS_SIGNING_IDENTITY`, `MACOS_CERTIFICATE`, `MACOS_CERTIFICATE_PASSWORD`, `APPLE_NOTARIZATION_KEY`, `APPLE_NOTARIZATION_KEY_ID`, `APPLE_NOTARIZATION_ISSUER_ID`                               |
| Windows                   | `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `ACCOUNT_NAME`, `CERT_PROFILE_NAME`, `ENDPOINT`, `WINDOWS_SIGNING_PUBLISHER`, `FILE_DIGEST`, `TIMESTAMP_DIGEST`, `TIMESTAMP_SERVER` |
| Linux                     | `LINUX_SIGNING_KEY`, `LINUX_SIGNING_KEY_PASSWORD`, `LINUX_SIGNING_KEY_FINGERPRINT`                                                                                                               |
| Website after publication | `AMPLIFY_REBUILD_WEBHOOK` for the existing approved site; independently verify its app/branch                                                                                                    |

See [Copper signing](./copper-signing.md) for Apple Developer ID/account and
notary-key provisioning, Azure public-trust profile/principal roles, GPG key
management, service costs/prerequisites, rotation, and failure recovery. These
accounts/services have not been created or purchased by this implementation.
Provision credentials, qualify actual signed platform packages and existing product
release requirements, then enable `COPPER_RELEASE_ENABLED`. No configured secrets
or release-enable variables were returned by GitHub during the implementation
inventory on 2026-10-31. Production signing remains unverified until a separately
authorized live signing run succeeds.

## Maintainer sequence (after qualification)

The following commands are **operator instructions**, not implementation validation.
Use a reviewed commit on main whose required CI has passed, and choose a new version.

```sh
git fetch origin main --tags
git tag -a copper-vX.Y.Z <reviewed-main-SHA> -m 'Copper X.Y.Z'
git push origin refs/tags/copper-vX.Y.Z
gh workflow run release_prepare.yml --repo imagine-engineering/made --ref main \
  -f release_tag=copper-vX.Y.Z
```

For a prerelease use a valid tag such as `copper-vX.Y.Z-rc.1`. Review the successful
Actions run, all packages, signing evidence and notes in the draft at the repository's
Releases page, then explicitly click **Publish release**. Never retarget a release
tag. Pushing tags or main alone performs no release preparation or publication.

## Non-publishing validation

```sh
python3 -m unittest discover -s script -p test_product_release.py
python3 -m unittest discover -s script -p test_refresh_website.py
python3 script/test-production-signing
cargo test -p xtask --locked
cargo xtask products --check
cargo xtask workflows
cargo xtask check-workflows
cargo fmt --all -- --check
./script/clippy --no-all-features -p xtask
```

The Git-fixture tests create tags only in disposable local repositories. Policy
unit tests use fixtures and fake GitHub responses; they do not prove hosted signing,
notarization, Windows trust or production artifact execution. The ordinary main
push runs CI and signing contracts, never the preparation/draft operation.

## Explicit macOS-only qualification and preparation

Choose `preparation_scope=macos-only` in either manual workflow to build only
Copper's catalog-supported macOS targets (currently `aarch64-apple-darwin`).
The default `full` retains Linux, macOS and Windows requirements. Other products
are not enabled by this option. There is no implicit platform skip based on
missing credentials, and missing macOS credentials or trust verification fails
the selected job. App and DMG must both have Developer ID Application signatures,
secure timestamps, accepted notarization and valid stapled tickets.

First run the non-publishing workflow on the reviewed source ref:

```sh
gh workflow run release_signing_check.yml --ref REVIEWED_REF \
  -f version=0.1.0 -f preparation_scope=macos-only -f sign_artifacts=true
```

This uses the existing product-aware pipeline, including
`cargo xtask bundle --product rust` with explicit macOS target, phase and required
signing arguments. It submits to Apple and uploads Actions artifacts, but cannot
create a tag, release, or publication. Download and verify the signed artifact
and exercise its actual native-agent workflow before claiming qualification.
The signature receipt records the app, nested native code (including llama.cpp),
reviewed entitlements, secure timestamps, stapled tickets and Gatekeeper results.

After successful qualification, required exact-commit main CI, the catalog
`COPPER_MACOS_RELEASE_ENABLED=true` gate, and an existing tag at that eligible commit:

```sh
gh workflow run release_prepare.yml --ref main \
  -f release_tag=copper-v0.1.0 -f preparation_scope=macos-only
```

The resulting draft is labelled **macOS only**. Its scope is bound into the
ownership marker, bundle plans, verification receipts and checksums. A full
preparation cannot replace that partial draft, and reruns cannot mix different
commits, versions, scopes or newly timestamped artifact hashes. Review before
explicit publication. No tags are created or moved by either workflow.

Drafts are always excluded from update selection. Even after publication, a
macOS-only release is excluded from generic full-platform selection and Windows
or Linux selection. `script/product_release.py latest --product rust --channel
stable --platform macos` explicitly opts into macOS selection and requires an
uploaded DMG. The default without `--platform` remains full-platform-only. The
existing updater remains disabled without a reviewed update service; this option
does not deploy or enable one. Full-platform website refresh skips partial
publication events and refuses manual partial-release refresh before a webhook.

On 2026-11-05, all six macOS repository secret names were present; their values
were not retrieved. No Windows/Linux signing secrets, release-enable variable,
or `copper-v0.1.0` tag were present at inventory time. Names alone do not verify
certificate validity or Apple authorization; hosted signing evidence is required.

The separate macOS gate never enables full-platform preparation. The existing
`COPPER_RELEASE_ENABLED` gate and Windows/Linux requirements remain unchanged
for `preparation_scope=full`. An administrator enables only the qualified scope
after reviewing actual signing and runtime evidence. Neither gate is set by the
workflow or this implementation.
